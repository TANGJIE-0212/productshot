# ProductShot 交互方案：原生表单做决策，网页做视觉编辑

记录日期：2026-09-23。

状态：已确认的产品方向与网页原型实现记录；不是整条真实制作流程已经实现或通过验收的声明。

## 2026-09-28 两种制作模式与统一分镜工作区

此节优先于下文早期网页说明。浅色 neo 与深色 spatial 共用逻辑，保留四步导航及可选场景，不添加网页聊天或模型桥接。

- **一键成片**：新草稿默认模式，默认直接介绍功能。完整产品目标是按真实可执行性推荐多个功能，逐步展示功能、脚本、录制及结果后继续；不是把业务场景当作必经环节。
- **分步骤成片**：用户可编辑每步，通过「确认并继续」推进。本地确认不构成导演项目审批，更不授权真实产品写入、录制、付费或发布。
- 首页不单独设置制作模式栏：输入框顶部是产品 / 参考视频链接与添加资料，中间是视频目标，底部两个提交按钮「一键成片」「分步骤成片」直接选择模式并开始。后续步骤保留模式切换及进度 / 暂停控制，深浅两版共用布局。
- **目前原型仅支持「示例自动演示」**：提交 Biz Table 示例后，依次显示已有功能证据、所选功能的分镜及参考图，最后直接载入已有真实录屏重新剪辑的参考样片；不再插入独立的讲解稿停留页。每屏约 4.5 秒的定时切换只是阅读停留，不是分析、生成、录制或渲染进度。结果始终标明不是按当前草稿新制作的视频。
- 默认推荐仅包含已有实录证据的**表单收集、视图与 Dashboard**。Agent 建表有文档和工具验证，但自然语言输入及 Agent 执行窗口未入镜，不默认勾选。导入、工作流、Teams、补充功能及业务场景均不能直接自动演示为已验证结果。
- 自动过程可暂停 / 接管；输入、模式切换、导航及隐藏页面会取消待执行跳转。刷新恢复为暂停，完成后刷新不会重播；恢复需明确点击。旧草稿没有模式字段时迁移到分步骤，保留已有勾选、介绍方式和编辑内容；模式切换不静默重置这些选择。
- 首页明确选择「一键成片」并提交 Biz Table 示例时，按已实录推荐重新选择表单、看板及逐功能介绍；旧场景、补充功能文字和已编辑脚本仍保留，不因重选而删除。过程中的暂停后继续则沿用当前选择，不重置编辑。
- 非示例来源或新增附件保持真实的「分析尚未开始」状态；修改来源立即解除旧示例关联。缺少素材、图片 / 视频错误、保存错误或跨标签草稿冲突都会停止自动推进，不用替代动画制造成功。
- 第三步「分镜脚本」只保留**一个分镜工作区**，不设置独立「讲解脚本」标签或第二套编辑流程。每一幕把画面、**这一幕的讲解**和录制细节放在一起：
  - **录制细节**面向执行者，保留确切输入、操作、等待和删减、结果验证、镜头、高亮及转场；这里可以有内部核验计数或技术证据。
  - **这一幕的讲解**面向观众，说清产品能力及价值，而非逐项朗读点击步骤、字段数量或服务器回执。讲解与操作在数据和用途上分开，但在同一幕中编辑。
- 讲解正文沿用旧 `shot.narration`；已有开场和收束（`narrationDrafts`）保留在同一工作区的紧凑、默认折叠「开场与收束」中，不丢弃用户编辑。旧 `scriptView` 值仍可读取，但不再决定页面或自动流程。逐功能和场景分支独立；各场景完整录制 / 讲解片段另存 `scenarioShotDrafts`，当前场景继续保留兼容的 `shots` 字段。历史用户改写的讲解不被新默认文案覆盖。
- 讲解草稿修改不会自动改变视频音轨。预置样片来自已有真实素材重新剪辑；不是网页即时执行的新录制。真实 Agent、执行授权、录制与按稿配音链路仍未接入此网页。
- 新版 Biz Table 参考讲解使用 Edge TTS `zh-CN-XiaoxiaoNeural`（晓晓），仅在结果页默认折叠展示六段原文及配音时间，不在分镜工作区放重复全文。配音时段为 0.4–9、9.5–16.3、16.9–22.2、23–44.8、46–57.7、59–75.1 秒；保留旧素材的片段跳转时间，不把音频入点当作录制切点。
- 最新故事方向应突出 **Agent 左侧输入 → 产品右侧变化**，而非将通用表单 / 看板操作当作产品核心故事。当前素材尚未录入 Agent 输入与执行过程；此方向需要新的可验证拍摄设计，不能将未录制的交互标成已实录，也不因改写脚本就冒充已有画面。
- 验证使用会话内启动并关闭的 Puppeteer 浏览器，不打开集成浏览器标签页。覆盖两种主题、自动推进 / 暂停 / 手动确认、刷新、来源变化、缺失素材及独立脚本持久化。

## 2026-09-25 UI 流程更新

以下为最新网页原型方向，优先于下文旧的 intake 顺序；尚未接通真实 Agent 分析。

- 主流程固定四步：**产品与目标 → 功能选择 → 分镜脚本 → 效果与修改**。场景故事不占主流程步骤。
- 首页收集产品 / 参考视频等资料链接和「视频目标」（用于什么场合、给谁看、希望说明什么），不再在功能页单独收集受众。
- 视频目标接受一句粗略描述，例如“向 LT 汇报 Biz Table 项目，时长约 1 分钟”；不要求提前列功能、业务场景或录制步骤，时长也是可选信息。
- 功能页逐条列出已整理功能，可多选；「＋ 添加功能」新增独立可编辑、可删除、可勾选的补充项，不限制补充项数量。补充功能保持待核验。
- 默认「逐个功能介绍」，直接进入分镜。功能页简列至少三个业务场景，让用户理解另一种介绍方式；只有用户选择「用场景介绍」并继续，才进入可选的场景故事中间页。
- 可选场景页归属于第二步；主导航始终四步，返回路径按所选介绍方式调整。已有用户明确选择的介绍方式保留，不因默认值变化覆盖。
- 场景路径保留使用人群、痛点及至少三个具体业务系统建议；自定义场景及每个场景的大纲独立保存。
- 2026-09-28：场景选择区只显示简短选项；选中场景的使用者、痛点、故事、预期结果和功能串联大纲统一在下方展开编辑，切换时保留各自草稿。深色与浅色版共用布局与交互，仅视觉主题不同。
- 首页提供 Repo / LT 汇报与网页 / 黑客松评委两种填写示例，点击只填入链接和目标，不触发分析。Biz Table 示例填入后通过「保存并继续」进入已有示例的功能、分镜和效果页，不再设置独立的「查看 Biz Table 示例」首页入口；仍标明示例预览，未执行实时分析。其他链接或附带额外资料仍进入待分析状态，不套用 Biz Table 内容。界面不显示 C/E 版本标签，内部样式标识和本地草稿键保持不变。
- 逐功能路径仅为当前所选功能建立可编辑分镜模板，不把旧场景分镜当作新生成结果。增减功能保留未受影响的草稿；两条路径不相互覆盖分镜。
- A–E 共用交互逻辑，视觉样式和本地草稿相互隔离。旧受众和补充文本保留于草稿，不自动推断为已确认视频目标。
- 当前只保留 C、E 作为活跃方案，A/B/D 归档而不删除草稿。E 使用深色磨玻璃和动态 3D 装饰；只取消圆柱顶部的高亮闪动，其余动态保留，支持暂停及系统减少动态设置。
- 逐功能脚本默认全部展开；初始状态、操作步骤、结束状态并排显示，下方直接显示高亮、取景、旁白与验证。输入框随内容增高，减少留白，不额外设置镜头列表或空预览框。保留独立草稿。
- 上一步/下一步放回页面内容下方，等待结果后继续。功能和录制脚本先提供完整推荐草稿，用户可直接继续，也可以改动；下一步不意味着未经展示的方案已获批准，更不代表已执行录制。
- 脚本阅读采用左侧功能与录制步骤、中间匹配画面、右侧当前步骤细节；完整输入、剪辑、旁白和验证仍保留，避免一次展开全部文字。已有参考图必须标明来源；无匹配截图时不伪造画面。
- 接入真实 Agent 后，产品分析阶段显示实际 loading，脚本和截图允许渐进出现；区分等待、失败和缺少权限。当前原型不以定时器模拟已执行分析。
- Scenario 是粗粒度录制大纲（第一步、第二步讲什么）；分镜脚本是可照着执行的详细录制 script。必须给出具体起始页面、逐字输入指令或字段值、操作顺序、结束画面、等待与删减方案、高亮的出现/消失时机、取景和推近拉远、逐字旁白、屏幕文案及其出现时机、验证和段落衔接。“尚未排练”“打开某功能并验证”不能代替这些设计内容。
- 已知功能示例由 Agent 拟定具体建议，用户只需修改；资料不足的自定义功能明确保留缺口，不假造产品行为。方案不等于已执行：首次拍摄仍须确认入口和权限，长等待剪辑要保留因果并标明缩短，不能把预置结果冒充即时生成。

## 1. 核心决策

- MCP 提供跨 Agent 的工具、原生表单请求和项目持久化；Skill 可作为导演方法的补充，不是 MCP 入口的必要依赖。
- Agent 负责理解产品、分析证据、推荐功能与受众、提出场景、生成及修改分镜。网页不另建聊天机器人或模型服务。
- 前三个阶段优先使用原生 MCP Elicitation；复杂分镜和预览使用同一个网页工作台。
- 不再先询问“整个产品还是特定功能”，直接展示分析出的功能列表。
- 推荐项可以预填，但必须允许修改；默认值不是用户同意。
- 不依赖 MCP App 的消息请求唤醒 Agent。原生表单在 Agent 发起的工具调用内等待用户回复，确认后返回结果，让原工具链继续。
- 支持 MCP Apps 的宿主以后可内嵌同一个视觉工作台；MCP Apps 不是第一版的必要条件。

## 2. 表单 1：收集产品信息

**目标：** 用户不需要先准备完整的演示 brief。

- 提供一个主要输入区，允许混合填写产品网址、Repo 地址、本地仓库路径、文档链接或路径，以及补充说明。
- 不强迫用户先选择资料类型，不要求每类资料都填写。
- 用户已经提供的信息应预填或复用，不重复询问；只有缺失或无法访问的资料才追问。
- 原生表单的文件上传能力取决于宿主；不能把输入路径描述成已经上传或读取文件。
- 用户提交后，Agent 明确显示“正在分析中”，然后执行真实的产品检查。
- 尽量全面梳理可展示能力，区分源码验证、运行验证、仅有文档和待确认。不能把局部检查称为“所有功能已验证”。

**结果：** 产品来源与补充信息，以及带来源、置信度、可见成功证据和限制的功能清单。

## 3. 表单 2：选择功能与初步受众

在同一次收集中完成，不另加展示范围选择。

### 功能

- 多选列表，默认勾选证据充分、适合展示且可形成连贯演示的组合。
- 用户可增加、取消推荐项，也可以填写未列出的新功能，或仅填写自定义功能。
- 自定义功能在检查之前仍为待验证，不因用户输入就视为已实现。
- 恢复项目时，已有明确选择优先于推荐值，包括仅有自定义内容的选择。

### 受众

- 根据产品和推荐展示内容，提供几个有依据的受众选项及简短理由。
- 默认推荐一个主要受众，支持替换、补充或自行填写；不把产品使用者直接等同于视频受众。
- 用户修改功能后，Agent 在提交结果中检查受众建议是否仍适合，必要时说明并调整，不静默覆盖用户选择。
- 表单 3 沿用此处的受众，不再次从头收集。

**结果：** 用户明确选择的功能、补充功能和初步受众。

## 4. 表单 3：确定受众、场景与大纲

- 至少提出 **3 个不同的场景候选**，不是同一个方案换标题。
- 场景指串联所选功能的具体业务系统，例如小超市进销存、HR 候选人管理、项目管理；不是“前后对比”“功能演示”等视频表现形式。
- 先分析产品使用者与痛点，再说明每个场景的业务故事、功能串联、预期结果与验证条件。产品使用者与视频受众分别记录。
- 场景设计首先研究产品/功能解决问题的机制，比较各人群的痛点重要性、产品适配程度、相对现有做法的收益，再按受益程度排序并推导场景。不能先选熟悉的场景，再反向凑功能。
- 推荐需解释“谁最受益、为什么、如何在场景中清楚展示收益”。视频渠道/观众影响选材和讲法，不改变产品人群与痛点；易录制、功能覆盖或证据格式不是主要排序依据。可执行性作为单独限制说明。
- UI 原型保留三张建议卡片与下方大纲的布局，分析依据放在可展开详情中；允许添加独立自定义场景，切换时保留各自草稿。原型中的建议是示例，不代表 Agent 已执行分析。
- 每个场景包含：具体任务或背景、要证明的价值、按演示顺序排列的功能/步骤大纲，以及所需条件和主要限制。
- 以执行可行性、功能证据、环境和权限准备情况排序；最可执行的场景排第一，并预选它及其对应大纲。
- 场景候选和最终选定的大纲是不同概念，不把三个候选一起当作用户已经选定的三个章节。
- 用户可以选择一个场景、补充自定义场景、组合候选或修改大纲。
- 用户可以自然语言表达修改，例如“用第二个，去掉第三步，最后加表单提交”；由 Agent 整理成完整的新大纲，不要求用户填写 JSON。
- 沿用并显示上一步受众，允许修改。用户更改后，重新检查场景是否适合。
- 对大纲有实质修改时，先展示修订后的完整版本再确认；不得把对旧草稿的确认当作批准新版本。

**结果：** 已确认的受众、场景与有序大纲。确认后才能生成正式分镜草稿。

## 5. 表单 4／工作台：生成和调整分镜

推荐使用网页展示和编辑复杂内容，原生表单负责修改意图、确认与继续。

### 网页布局

- 左侧：镜头列表、顺序和当前状态。
- 中间：当前镜头的画面、素材或预演。
- 右侧：当前镜头的可编辑细节。

这是视觉工作台自身的布局，不是强制所有 Agent 都采用固定的聊天左右分栏。

### 镜头细节

至少包括目的、起始状态、录制内容、实际操作顺序、结束状态、证据、素材类型、highlight 目标及出现/消失时机、缩放和取景、保留的界面上下文、等待条件、转场、验证方式和不可丢失的要求。

- 先由 Agent 提出完整草稿，用户不必逐字段创作。
- 支持直接编辑，也支持在对话中说“这镜先展示空表，再开始建表”等自然语言修改。
- 保持因果顺序，不提前显示结果；不把重建界面或动画当作真实产品操作。
- 修改保留镜头 ID、历史和未受影响的内容；涉及已确认内容时使相关确认失效，不删除后续草稿。

### 网页和原生对话的衔接

目标流程：

1. Agent 打开当前项目的视觉工作台。
2. 网页编辑自动保存，并清楚显示保存中、已保存或失败；保存不代表审批。
3. Agent 在原生确认工具中等待用户。
4. 用户编辑完成后，在原生表单选择“按当前版本继续”或提出修改。
5. 工具检查是否存在未完成的保存以及版本冲突，读取用户实际确认的最新版本，再返回给 Agent。

**此衔接尚待实测和具体实现。** 必须避免用户确认时网页仍有未保存草稿、长时间等待超时或多人编辑导致批准错误版本。取消、失败或超时不能视为确认，也不能声称网页会自动唤醒 Agent。

## 6. 预览与修改

- 分镜编辑与预览留在同一个工作台，减少切换。
- 第一版优先提供明确标注的 **分镜预演**，用于判断画面顺序、重点和镜头衔接；不能声称它是实际产品录屏或成片。
- 用户可以根据预演直接改某一镜或给 Agent 提修改意见；只重新生成受影响内容，保留已确认要求。
- 真实录屏、配音、渲染和成片审阅属于后续制作链路，需要单独实现、验证和授权。
- 未产生并检查实际媒体文件时，不展示虚假的制作完成状态。

## 7. 跨宿主、状态与授权

- 支持本地 stdio MCP，不等于支持 Elicitation；支持 Elicitation，也不等于支持 MCP Apps。
- 原生表单要求客户端声明 `elicitation.form`；兼容旧式 `elicitation: {}`。仅支持 URL 模式的客户端不能当作支持原生表单。
- 控件样式、布局、多选和默认值显示由宿主实现，须逐宿主实测，不承诺所有 Agent 体验相同。
- 不支持表单时明确降级为聊天收集用户的显式答案，再调用保存工具。
- 项目数据保持私有，不提交来源内容、对话、凭据或录制数据到公共仓库。
- 保存、用户确认、阶段审批和制作授权是不同事件。分镜审批不授权修改产品、录屏、付费服务、上传或公开发布。
- 保存与确认必须检查 revision。拒绝、取消、无效输入、网络失败和超时均不自动保存或推进。

## 8. 当前实现与后续验收

### 当前已有

- 版本化的本地导演项目、阶段校验、历史和原有网页编辑器。
- MCP 功能分析发布、项目读取和显式功能保存工具。
- `productshot_select_features` 已改为等待原生 Elicitation 表单，接受后保存并返回；自动化测试覆盖等待、接受、拒绝、取消、默认项、已有选择、无效答案和版本冲突。
- 可选的 `productshot_open_feature_app` 保留用于试验，不作为默认 intake。

### 不得视为已完成

- 原生表单在当前宿主中的完整提交后续聊验收。
- 表单 1 的混合来源收集，以及表单 2 合并受众的实际实现。
- 至少三个场景的原生选择、自定义场景和大纲修改链路。
- 分镜网页自动保存与原生“按当前版本继续”的可靠衔接。
- 分镜预演及真实录制、配音、渲染制作链路。
- 其他 Agent 的跨宿主兼容验收。

验收标准是用户在支持的宿主确认原生表单后，Agent 获得实际答案并继续，不再要求用户另发“已提交”。对于复杂网页编辑，保留一次明确的原生确认，不伪装成全自动回调。

## 9. 协议依据

- [MCP Elicitation 规范](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)：在工具调用内请求用户输入，区分接受、拒绝与取消。
- [MCP Apps 规范](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)：宿主控制 UI 与消息交互，App 消息不构成跨宿主的自动续聊保证。
- [VS Code 关于 App 消息发送确认的维护者说明](https://github.com/microsoft/vscode/issues/317519#issuecomment-4509473369)：不能依赖 `ui/message` 在该宿主自动发送新一轮对话。
